# #552 Wave E — real keyboard behavior in five original cross-component controls

**2026-10-20. Live native Chrome and Edge keyboard observation on the unchanged .NET 10 Blazor WebAssembly debug demo.** Completes the previously *prepared but unexecuted* standalone keyboard handoff. Audit only; **not a component fix, not Fluent visual/behavioral parity approval, not native OS screen-reader (NVDA/JAWS) validation, and not an approved Penpot/Figma design**. See [earlier pointer/ARIA evidence](FLUENT-PARITY-CROSS-CONTROL-ICON-AX.md) for comparison.

## Method and repeatability

- Repro on isolated v3 audit branch: build original `src/Bluent.UI.Demo/Bluent.UI.Demo.csproj` if needed, then run `node scripts/quality/probe_v3_cross_component_keyboard.mjs chrome` and repeat with `edge` from repo root. The script was derived from the already validated Wave D native browser harness, with a corrected CDP `Input.dispatchKeyEvent` sequence (`keyDown` with Enter/Space text, `keyUp`) cross-checked against existing Bluent browser QA scripts.
- Each run opens an isolated local demo server plus a dedicated temporary Chrome/Edge profile, uses true Chromium CDP **keyboard Tab / ArrowRight / ArrowLeft / Enter / Space** events, and cleans up those **owned** process trees. It reads DOM Focus, source CSS selection and aria attributes; mouse click comparisons are still performed separately on the unmodified demo. No JS keyboard events are fabricated or injected into product code.
- Modes: **Light/LTR**, **Dark/RTL**, and **CSS Forced Colors emulation**. Five cases per mode/engine: TabList Small/First Tab, NavList Components disclosure, Accordion header 1, MenuList Disabled Items/Undo, and MenuList Disabled Items/Paste (enabled item). Total **Chrome 75/75 + Edge 75/75 = 150/150** checks across **30 real browser cases**, proving measured outcomes and fixture validity, **not** acceptance or a passing accessibility grade.
- For natural Tab reachability the test focuses the actual preceding *existing* tabbable element, then presses **native Tab** and observes the resulting document.activeElement. Separately, `.focus()` on the target is a **diagnostic**, not proof of natural Tab access. When a DIV fails to focus, no false claim that Enter/Space were dispatched to that DIV is made; it has no valid active-element key target. Deliberately no external links are activated.

## Observed results (identical in Chrome and Edge, three modes)

| Original existing component | Native keyboard observation | Implication, not implemented fix | Owner |
| --- | --- | --- | --- |
| **TabList / icon-labeled First Tab** | Native Tab from actual preceding button focuses the `button.tab-item`; its DOM tabIndex is **0**. While first tab has focus/selection, native **ArrowRight** and **ArrowLeft** do **not** move focus or selection. Focusing the Second Tab (as setup), native **Enter** selects it, deselecting First; focusing First and pressing native **Space** selects First again. AX still says generic native button, not `tab`; `aria-selected` missing; accessible name contains private-use icon font codepoint. | Native button Enter/Space works; missing tablist roving arrow keyboard model, semantic tab state and decorative glyph naming, but do **not** claim whole TabList lacks keyboard activation. | [#465](https://github.com/vrassouli/Bluent/issues/465) |
| **NavList / expandable Components** | A preceding `Getting started` navigation link can be focused; pressing native Tab **skips the clickable Components wrapper**, landing on child `Buttons` link. Its actual wrapper is a `div`, tabIndex **-1**, and direct DOM `.focus()` fails. Earlier pointer test expands it. | Provide a separately focusable, named disclosure trigger, `aria-expanded`, keyboard and nested-link-safe focus pattern, after design review. | [#466](https://github.com/vrassouli/Bluent/issues/466) |
| **Accordion / first header** | Native Tab from an existing preceding link skips the clickable header; `div.header` tabIndex **-1**, `.focus()` fails. Earlier pointer click expanded the parent. | Focusable native disclosure button in heading, with `aria-expanded`, label, keyboard contract, safe nested action behavior. | [#469](https://github.com/vrassouli/Bluent/issues/469) / [#507](https://github.com/vrassouli/Bluent/issues/507) |
| **MenuItem / disabled Undo** | Original `div.menu-item.disabled` with a `disabled` attribute is **not** in natural Tab flow (tabIndex **-1**); direct `.focus()` fails. AX is generic with no exposed disabled state, not semantic `menuitem`/`aria-disabled`. | Do not interpret skipping disabled item as accessibility success; define menu role/disabled semantics with parent MenuList and keyboard focus management. No disabled click attempted here. | [#517](https://github.com/vrassouli/Bluent/issues/517) |
| **MenuItem / enabled Paste** | Even the **enabled** `div.menu-item` is skipped by native Tab, has tabIndex **-1**, and direct `.focus()` fails. | Confirms keyboard issue is **not limited to disabled items**. Determine menu-specific roving focus/arrow control vs Tab according to approved MenuList interaction contract; no assumption that each menu item should always be a standalone Tab stop. | [#517](https://github.com/vrassouli/Bluent/issues/517) |

**Important design nuance:** ARIA menu composites often use a *single tab entry* with arrow-navigation among menuitems; being absent from Tab stops alone is not dispositive if a parent has proper focus management. Here, original rendered MenuItem nodes also have generic AX roles and the standalone original MenuList demo has no demonstrated native keyboard menu navigation. The defensible finding is **no keyboard focus path in these measured original specimens**, not a blanket rule that every individual MenuItem must be a Tab stop.
