## Measured opaque text pair contrast (10 branded themes × 2 modes)

`python scripts/quality/audit_v3_theme_contrast.py` or `--json` scans compiled `theme-<brand>-{light,dark}.css` and computes relative luminance and contrast ratios for four **semantically plausible existing token pairs**:

1. `colorNeutralForeground1` on `colorNeutralBackground1`.
2. `colorNeutralForegroundOnBrand` on `colorBrandBackground`.
3. `colorNeutralForegroundOnBrand` on `colorBrandBackgroundHover`.
4. `colorNeutralForegroundOnBrand` on `colorBrandBackgroundPressed`.

All 80 possible pairs used opaque hex colors that the scanner could evaluate; **0 were below 4.5:1**. The **lowest ratio was 5.552:1** (Excel light Primary and Excel dark Primary-hover). This is a reassuring *baseline*, not a WCAG 2.2 AA audit or proof of a particular control's **rendered** color. Decorative colors, disabled controls, validation states, composite surfaces, shadows, focus outlines, OS forced-colors, background images and independent app CSS are not assessed.

The scanner deliberately treats alpha or non-hex values as **unmeasurable**, rather than silently assigning them an inaccurate contrast. Mathematical regression tests run with `python -m unittest discover -s scripts/quality -p test_v3_theme_contrast.py -v` (**5/5 passing**), covering 21:1 black/white, same-color 1:1, short hex, alpha invalidation, and a known <4.5 sample.

The v3 design process must still validate focus and semantic state colors in the **real UI** before design acceptance. Do not claim 80/80 baseline pairs imply all colors are accessible.

## Forced-colors focus, mobility and control geometry (actual Blazor WASM lab)

Reproduce with running Debug demo and `node scripts/quality/probe_v3_dialog_theme.mjs http://127.0.0.1:5080`.

- Chrome DevTools emulates `forced-colors: active`, matches the OS media query and computes sample black background/white foreground. After dismissing the overlay, the script focuses the Name input and dispatches a **real Shift+Tab key event**, observing that focus moves to the **Preview overlay** Bluent button.
- At this moment `button.matches(':focus-visible')` is **true** and Chrome computes an outline of **2px solid rgb(26,235,255)**. This is **one browser/sample focus state**, not a full keyboard accessibility audit.
- Primary/lab buttons have a measured comfortable height **40px** (selected control widths around 119–125px), while compact mode at 390px viewport gives **32px** height with no document-wide horizontal overflow (`document.documentElement.scrollWidth === 390`). The Name input was approximately **38px** high.
- `prefers-reduced-motion: reduce` still sets the **demo-only** button transition to `0s`, but existing real `.bui-overlay` animation remains **0.25s** — a candidate motion policy gap requiring design decisions and targeted follow-up tests.

The recorded `passed` property from the dialog probe only asserts **correctly reproducing current light-Dialog vs local dark-content theme separation**. The accessibility measurements are diagnostic fields, **not** asserted as complete acceptance.

## SSR demo smoke: distinguish launch environment from a component regression

The **Debug-built** `Bluent.UI.Demo.SSR` compiled with **0 warnings/errors**. A local run with `--no-launch-profile` but without setting `ASPNETCORE_ENVIRONMENT` defaulted to **Production**:

- `GET /v3/styling-lab` → HTTP **200** (server-rendered HTML visible).
- `GET /_content/Bluent.UI/bluent.ui.components.min.css` → **500**.
- `GET /_framework/blazor.web.js` → **500**.
- Server log: `StaticAssetDevelopmentRuntimeHandler` attempted to read missing files at `src/Bluent.UI.Demo.SSR/wwwroot/_content/Bluent.UI/...css` and `wwwroot/_framework/blazor.web.js`.

Repeating the **same Debug-built host** with explicit `ASPNETCORE_ENVIRONMENT=Development` yielded **HTTP 200 for all three paths** (CSS length **117,963 bytes**, Blazor script **200,645 bytes**, route HTML ~27 kB). Therefore the initial 500 is attributable to a local **Debug build plus Production execution configuration mismatch** as reproduced; **it is not enough evidence to conclude that a true Release/published SSR host is broken**, nor that interactive server/WASM render modes work fully.

For a reproducible local static-SSR smoke run:

```powershell
dotnet build src/Bluent.UI.Demo.SSR/Bluent.UI.Demo.SSR.csproj -c Debug --no-restore --nologo -v:q
$env:ASPNETCORE_ENVIRONMENT = "Development"
dotnet run --project src/Bluent.UI.Demo.SSR -c Debug --no-build --no-launch-profile --urls http://127.0.0.1:5082
```

**Follow-up smoke (completed):** `dotnet publish src/Bluent.UI.Demo.SSR/Bluent.UI.Demo.SSR.csproj -c Release --no-restore --nologo -v:q -o <temporary directory>` succeeded. The temporary publish output included `Bluent.UI.Demo.SSR.dll`, `wwwroot/_content/Bluent.UI/bluent.ui.components.min.css` (**117,963 bytes**) and `wwwroot/_framework/blazor.web.js` (**200,645 bytes**). Running **that published output**, with `ASPNETCORE_ENVIRONMENT=Production` on `http://127.0.0.1:5083`, yielded **HTTP 200** for all three URLs, including `/v3/styling-lab` (HTML ~30 kB). Thus the initial Debug/Production asset error was **not reproduced** in a normal Release/Production publish. This is a positive **local published SSR static-asset smoke**, not a deployment, not full interactivity and not a guarantee about SSR rendering across all pages.

A future CI matrix should cover **Debug + Development** and **Release published + Production** separately with interaction and browser modes; do not mix build and host configurations when drawing conclusions.
