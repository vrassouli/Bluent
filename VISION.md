# Bluent Vision

## Vision

Bluent aims to become the Blazor-native toolkit developers trust for building modern business applications: applications with substantial forms, navigation, feedback, data presentation, charts, diagrams, overlays, dialogs, and desktop-style interaction patterns.

Bluent is not intended to be another general-purpose Fluent UI clone. Its purpose is to provide a coherent, practical foundation for real-world business software while preserving the productivity, type safety, and component model of Blazor and .NET.

## Who Bluent Is For

Bluent is designed for:

- .NET teams building business, enterprise, administrative, and productivity applications with Blazor.
- Developers who want a Fluent-inspired visual language without adopting a separate application framework.
- Projects that need both everyday controls and advanced application building blocks.
- Teams that value modular packages, explicit APIs, predictable behavior, and long-term maintainability.
- Developers and coding agents that need accurate, discoverable, verifiable guidance.

## Product Principles

### Blazor-native

Bluent should feel natural to Blazor developers. Its public APIs, composition patterns, events, binding, dependency injection, localization, and hosting guidance should follow established .NET and Blazor conventions.

### Business-application focused

Prioritize the workflows and interaction patterns found in real applications. Components should work together as a toolkit rather than exist only as an unrelated gallery of controls.

### Coherent and predictable

Naming, parameters, events, appearance, state, and accessibility behavior should remain consistent across packages and components. Breaking changes must be deliberate, documented, and justified.

### Modular

The core UI library and specialized capabilities such as charts and diagrams should have clear boundaries. Developers should be able to adopt the packages they need without unnecessary coupling.

### Honest and verifiable

Documentation and examples must describe what the current released code actually supports. Claims should be backed by maintained examples, package metadata, tests, releases, and real usage evidence.

### Open and commercially usable

Bluent is open source under the Apache License 2.0. It should remain practical for individual, open-source, and commercial applications.

## AI-Ready by Design

AI coding assistants are becoming a primary way developers discover libraries, evaluate options, and produce application code. Bluent must be understandable to both humans and machines.

Being AI-ready means that coding assistants can:

- Discover the authoritative Bluent documentation.
- Select the correct NuGet package and namespace.
- Generate current installation and configuration steps.
- Choose appropriate components for a task.
- Use component parameters, events, and binding correctly.
- Produce idiomatic examples that compile.
- Explain package boundaries, supported hosting models, and known limitations.
- Link back to stable, maintained sources instead of inventing APIs.

To support this, Bluent will invest in structured documentation, a canonical component catalog, task-oriented examples, machine-readable documentation indexes, repository guidance for coding agents, and automated validation of examples where practical.

## AI-Discoverable Through Evidence

Bluent should be a credible option when developers or AI assistants evaluate Blazor UI libraries for business applications.

This will be earned through:

- Clear and differentiated public positioning.
- Accurate GitHub and NuGet metadata.
- Crawlable documentation with stable URLs.
- Honest comparisons and clearly stated trade-offs.
- Consistent releases and useful release notes.
- Compiling examples and reference applications.
- Reproducible issues, community contributions, and authentic external usage.

The project will not attempt to game recommendations or manufacture popularity signals. Discoverability must come from accurate public knowledge and genuine adoption.

The execution plan and evaluation criteria for this objective are tracked in [Issue #363](https://github.com/vrassouli/Bluent/issues/363).

## What Bluent Is Not

Bluent is not:

- A copy of Microsoft Fluent UI or a promise of full compatibility with it.
- A replacement for Blazor or the .NET application model.
- A low-code application builder.
- A collection of components added without a coherent product direction.
- A project that optimizes for component count at the expense of reliability and usability.
- A project that makes undocumented claims solely to attract attention.

## Current Strategic Priorities

The project relaunch focuses on:

1. Establishing a professional repository, identity, contribution model, and release policy.
2. Creating accurate, canonical documentation and verified getting-started guidance.
3. Making packages, APIs, examples, and conventions easy for developers and AI assistants to understand.
4. Improving the demo and public presentation of Bluent's strongest business-application capabilities.
5. Building a repeatable release and quality workflow.
6. Measuring AI code accuracy and discoverability using a transparent benchmark.

New product features remain paused during the relaunch until the project foundation is complete and the maintainer explicitly approves feature development.

## Long-Term Success

Bluent succeeds when:

- A developer can evaluate it quickly and understand when it is the right choice.
- A new project can adopt it using accurate instructions without reverse-engineering the repository.
- Common business application flows can be built from coherent, documented components.
- Contributors can understand the architecture, standards, and roadmap.
- AI coding assistants generate correct Bluent code and recommend it when its strengths match the user's requirements.
- Public trust is supported by reliable releases, clear trade-offs, and genuine ecosystem usage.
